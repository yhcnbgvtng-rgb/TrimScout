# TrimScout Issues Parking Lot

Tracking only — nothing in this file has been acted on except where explicitly noted as fixed below. Compiled from the overnight data-correctness and functional/UI audits (2026-08-27), earlier findings, and tonight's session (2026-08-28). Organized by which brand's pipeline owns each issue — Cross-Brand issues live in shared code/data paths (the modal, search, the API layer) and affect every make the same way, so fixing one instance there fixes it for all three. Update this file as new issues surface or existing ones get resolved; do not fix anything still listed as open without explicit go-ahead.

## Cross-brand

- **Vehicle detail modal is hardcoded to Porsche for every brand.** [Critical, open] Confirmed independently by both audits. A real 2026 Chevrolet Colorado (Bellavia Chevrolet) shows a fabricated "6-Speed Manual / PDK" (Porsche-only tech), a wrong "Flat-4" engine description, and a hardcoded **$222,500 fake MSRP** on a truck that really costs ~$45K. This affects roughly 2/3 of all inventory (every Ford and Chevrolet vehicle) — also confirmed on a Ford F-150 (V6 EcoBoost mislabeled "3.5L Flat-6" — flat/boxer layouts don't exist on Ford or GM engines at all). No `make` check exists anywhere in the component. Source: `components/LightsailIntelligence.tsx` (modal) + `app/api/porsche-sticker/route.ts` (hardcodes `make: "Porsche"`, confirmed live via curl on the same VIN, also returns the same fabricated $100,000/$222,500-style baseMsrp fallback). **Partially addressed 08-28** (per explicit instruction, unrelated to this audit): the "Sole Source: finder.porsche.com" badge, "Paste Build Text" OCR flow, and "Porsche Finder Inventory" button were removed from the modal. The underlying hardcoded-Porsche engine/transmission/MSRP fallback logic itself was **not** touched and is still live for every non-Porsche vehicle. (The Taycan-specific slice of this falsy-zero bug is fixed — see Porsche section.)
- **VIN search returned zero results for every VIN, on every brand — FIXED 08-28.** Searching a confirmed-valid VIN, or even a substring of one, returned zero results despite the search bar's placeholder text explicitly advertising VIN search; model/dealer/option-name search all worked correctly. Root cause: `buildSearchText()` in `scrapers/lightsail-crawler/src/db.js` never included the vehicle's own VIN in the `search_text` column it builds — only year/make/model/trim/bodyStyle/dealerName/state/exteriorColor/option names. FULLTEXT and LIKE search were both correctly returning zero rows because the VIN was simply never indexed. Fixed the builder, deployed to `porsche-tracker` and `porsche-finder-tracker`, and backfilled `search_text` for all 485,663 existing vehicle rows (Porsche+Ford+Chevrolet) directly against the live DB so the fix applies immediately, not just to future crawls. Re-verified live with the exact VIN originally reported broken (`WP0AA2A94TS207803`) — now returns correctly. Committed.
- **Over-paginating permanently breaks the results view.** [Critical, open] The "Next" page button never disables at the true last page (304), so it's easy to overshoot; once you do, the grid replaces itself with "No vehicles match your active filters" — and even clicking "Reset All Filters" doesn't recover it. Only a full page reload fixes it.
- **An `autodev` third-party API key is exposed in plaintext in a client-side network request on every page load.** [Critical, open] (Distinct from the separate hardcoded Auto.dev key already flagged in source earlier this session — this is confirmed happening on the live production page itself, visible to anyone via browser devtools.)
- **214 Chevrolet + 377 Ford vehicles fall back to a hardcoded $222,500 Porsche MSRP.** [Critical, open] Vehicles with no real price and no real base MSRP fall back to a literal hardcoded "$222,500 Porsche Window Sticker MSRP" regardless of brand.
- **Ford and Chevrolet dealers have no geocoded coordinates at all.** [High, open] Unlike Porsche (now fixed — see Porsche section), Ford's 1,827 and Chevrolet's 1,925 dealers have never been geocoded, so their distance badges still fall back to the ~20-city hardcoded approximation.
- Most filters (Trim, State, Body Style, Price Range, Days on Lot) correctly narrow results but never show a removable "chip" the way Make/Model/Sort do — users get no visual confirmation of what's currently applied. [Medium, open]
- Mojibake in rendered text — "Coupé" showing as "CoupÃ©" (an encoding issue somewhere in the pipeline). [Medium, open]
- Price-drop badge visually clips/overflows on large discount amounts. [Medium, open]
- Mobile layout (375px width): the condition badge overlaps the mileage badge on vehicle cards, and dealer names wrap badly. [Medium, open]
- trimscout.com had no Open Graph or Twitter Card meta tags at all, so link previews in iMessage/Slack/Twitter had nothing to render. **Fixed 08-28**: added real OG/Twitter metadata plus a dynamically-generated, on-brand `og:image` (no static asset existed to reuse). Deployed and confirmed live. [Medium]
- **The "Daily Activity" tab silently ignoring active filters — FIXED 08-28.** Now shares the same `buildFilterParams()` the Results tab uses, so every active filter (search/model/trim/condition/dealer/state-or-radius/bodyStyle/year/price/mileage/daysOnLot/opportunity/optionCode) applies there too. [Medium]
- The `daysOnLot` display fix (real values now render correctly — 0d/2d/4d confirmed live, not a fake constant 14). [Clean, fixed]
- The `dealer_city` field-mapping / distance-badge fix (varies correctly by dealer location, stays consistent within one dealer). [Clean, fixed]
- Mock/fixture data (`MOCK_VEHICLES`, hardcoded fallback fixtures) is properly isolated from the main browsing UI — confirmed not leaking into what users actually see. [Clean, fixed]

## Porsche

- **Distance badge collapsed to state-level, not per-dealer — FIXED 08-28.** Confirmed: Richmond and Arlington, VA — ~100 real miles apart — both showed "321 mi." Porsche's 216 dealers already had real geocoded lat/lng (`scrapers/lightsail-crawler/dealers.json`, added to build the Finder-crawler's search origins), but it wasn't wired into the `dealers` DB table or the distance-badge calculation. Added latitude/longitude to `upsertDealers()`, the inventory API's SELECTs, and the frontend's distance calc (`db.js`, `inventory_api_server.js`, `lib/lightsailClient.ts`, `components/LightsailIntelligence.tsx`). All pieces committed and deployed (box + Vercel production). The `dealers` table itself will show real coordinates once the next scheduled Porsche crawl runs `upsertDealers()` again — not retroactive without a crawl. [High]
- **Porsche Naples' price-extraction bug — FIXED 08-28.** Root cause was `standalone.js`'s last-resort price regex matching the *first* `"price"` key anywhere on the page instead of one scoped near the vehicle's own VIN (confirmed live: it was picking up unrelated figures like a finance-calculator payment). Fixed and deployed to `porsche-tracker` and `ford-nj-tracker`; committed to the repo. [High]
- **Vehicles falsely marked "sold" — FIXED 08-28.** Root cause: any dealer whose crawl failed for *any* reason (bot-blocked, timeout, template break) had its entire previously-active inventory marked SOLD on that day's diff. Fixed: a vehicle whose dealer produced zero real evidence that run now carries forward unchanged instead. Deployed to `porsche-tracker` and `ford-nj-tracker`; committed to the repo. [High]
- **Two uncoordinated schedulers for the Porsche daily crawler — FIXED 08-28.** OS crontab + PM2's own `cron_restart` were confirmed both firing `node src/standalone.js` in the same directory at the identical schedule (`0 6 * * *`) — a genuine duplicate, not just a theoretical risk. Removed the redundant PM2 entry (`pm2 delete porsche-daily-crawler`, `pm2 save`) and kept the OS crontab as the single scheduler, matching how `ford-nj-tracker` was already set up. Confirmed via `pm2 list`/`crontab -l` that only one scheduler remains. [High]
- **Jack Daniels Porsche (Upper Saddle River, NJ) — reportedly the largest Porsche dealership in the country — was missing from the configured dealer list entirely.** Found 08-28 when the user asked where it appeared in the coverage audit and it wasn't there under any name. **Fixed**: added to `dealers.json` (216 dealers now), deployed to `porsche-tracker` and `porsche-finder-tracker`, committed to the repo. Not yet crawled for the first time. [High]
- **Porsche coverage: 190 of 216 dealers collecting (88%), up from ~41-42 (the ~19-20% ceiling documented in the original overnight audit).** Fixed 08-28 by adding a second discovery path — Porsche's own official nationwide inventory search (`finder.porsche.com`), reached via a stealth-patched headless browser (`patchright`) instead of scraping each dealer's own site. Confirmed live: plain HTTP and even a vanilla headless browser both get blocked by Porsche's Vercel "Security Checkpoint" (bot-fingerprint detection, not just IP reputation) from the crawler box's IP — `patchright` specifically evades that fingerprinting and gets through reliably. Root-caused via a live per-dealer classification (see `scrapers/lightsail-crawler/overnight-analysis-report.md` for the original breakdown: 115 Vercel checkpoints, 19 Cloudflare/WAF, 19 unreachable, 10 wrong sitemap path, 10 no real inventory in sitemap). This same technique does **not** transfer to Ford (`ford.com/inventory`) or Acura (`acura.com/inventory-results`) — both are blocked by Akamai with a static "Access Denied" (no JS challenge to solve), confirmed live including with `patchright`; that class of block needs a paid residential/rotating proxy service instead. [Medium]
- **The Sold/Removed feed shows a garbled "0 Porsche" title — treated as resolved 08-28.** Investigated: searched `DailyChangesPanel.tsx` in full (no "Porsche" string anywhere), searched `dashboard.js` (a different, internal-ops component that shows "Sold / Off-Market", not this string), and grepped broadly across `components/` and `app/` for count+brand template patterns with zero matches. Re-tested live the same night: loaded the Daily Activity tab against the full 21,732-vehicle inventory and got a clean, correctly-worded empty state ("No day-over-day comparison is available yet...") — no garbled title anywhere. No code change found or needed; most likely a side effect of the earlier Daily Activity filter-sync rewrite. [Clean]
- **Taycan (and other EVs) displayed a fake "Flat-6" engine — FIXED 08-28.** `nhtsa?.engineCylinders || 6` — Porsche EVs genuinely have 0 cylinders (real NHTSA data), but the falsy-zero fallback bug displayed a fabricated "Flat-6" instead of recognizing the vehicle as electric. Now explicitly checks `engineCylinders === 0` and renders "⚡ Electric". Deployed to Vercel production. [Critical]
