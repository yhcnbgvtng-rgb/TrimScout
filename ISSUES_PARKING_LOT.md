# TrimScout Issues Parking Lot

Tracking only — nothing in this file has been acted on except where explicitly noted as fixed below. Compiled from the overnight data-correctness and functional/UI audits (2026-08-27), earlier findings, and tonight's session (2026-08-28). Update this file as new issues surface or existing ones get resolved; do not fix anything still listed as open without explicit go-ahead.

## Critical (fabricated/misleading data on live production)

- **Vehicle detail modal is hardcoded to Porsche for every brand.** Confirmed independently by both audits. A real 2026 Chevrolet Colorado (Bellavia Chevrolet) shows a fabricated "6-Speed Manual / PDK" (Porsche-only tech), a wrong "Flat-4" engine description, and a hardcoded **$222,500 fake MSRP** on a truck that really costs ~$45K. This affects roughly 2/3 of all inventory (every Ford and Chevrolet vehicle) — also confirmed on a Ford F-150 (V6 EcoBoost mislabeled "3.5L Flat-6" — flat/boxer layouts don't exist on Ford or GM engines at all). No `make` check exists anywhere in the component. Source: `components/LightsailIntelligence.tsx` (modal) + `app/api/porsche-sticker/route.ts` (hardcodes `make: "Porsche"`, confirmed live via curl on the same VIN, also returns the same fabricated $100,000/$222,500-style baseMsrp fallback). **Partially addressed 08-28** (per explicit instruction, unrelated to this audit): the "Sole Source: finder.porsche.com" badge, "Paste Build Text" OCR flow, and "Porsche Finder Inventory" button were removed from the modal. The underlying hardcoded-Porsche engine/transmission/MSRP fallback logic itself was **not** touched and is still live for every non-Porsche vehicle.
- **VIN search is completely broken.** Searching a confirmed-valid VIN, or even a substring of one, returns zero results — despite the search bar's placeholder text explicitly advertising VIN search. Model/dealer/option-name search all work correctly, so this is isolated to VIN specifically. **Re-confirmed live 08-28** with a real VIN (`WP0AA2A94TS207803`, a genuine active 2026 911 Carrera at Porsche Main Line): browsing by dealer returns it correctly, searching its own exact VIN returns zero results.
- **Over-paginating permanently breaks the results view.** The "Next" page button never disables at the true last page (304), so it's easy to overshoot; once you do, the grid replaces itself with "No vehicles match your active filters" — and even clicking "Reset All Filters" doesn't recover it. Only a full page reload fixes it.
- **An `autodev` third-party API key is exposed in plaintext in a client-side network request on every page load.** (Distinct from the separate hardcoded Auto.dev key already flagged in source earlier this session — this is confirmed happening on the live production page itself, visible to anyone via browser devtools.)
- **Falsy-zero display bugs, same category as the already-fixed `daysOnLot` bug:**
  - `nhtsa?.engineCylinders || 6` — Porsche EVs (Taycan) genuinely have 0 cylinders (real NHTSA data), but display as a fake "Flat-6."
  - 214 Chevrolet + 377 Ford vehicles with no real price and no real base MSRP fall back to a hardcoded **$222,500** "Porsche Window Sticker MSRP" regardless of brand.

## High (real bugs, live and reproducible)

- **Distance badge collapses to state-level, not per-dealer.** Still a stopgap, not the real fix. Confirmed: Richmond and Arlington, VA — ~100 real miles apart — both show "321 mi." Proper fix needs real per-dealer lat/lng. **Partially undermined 08-28**: Porsche's 215 dealers now DO have real geocoded lat/lng (`scrapers/lightsail-crawler/dealers.json`, added to build the Finder-crawler's search origins) — but that data isn't wired into the `dealers` DB table or the distance-badge calculation yet, so the badge itself is unchanged. Ford/Chevrolet dealers still have no coordinates at all.
- **Porsche Naples' price-extraction bug — FIXED 08-28.** Root cause was `standalone.js`'s last-resort price regex matching the *first* `"price"` key anywhere on the page instead of one scoped near the vehicle's own VIN (confirmed live: it was picking up unrelated figures like a finance-calculator payment). Fixed and deployed to `porsche-tracker` and `ford-nj-tracker`; committed to the repo.
- **Vehicles falsely marked "sold" — FIXED 08-28.** Root cause: any dealer whose crawl failed for *any* reason (bot-blocked, timeout, template break) had its entire previously-active inventory marked SOLD on that day's diff. Fixed: a vehicle whose dealer produced zero real evidence that run now carries forward unchanged instead. Deployed to `porsche-tracker` and `ford-nj-tracker`; committed to the repo.
- **Wayne Ford's configured domain points to an unrelated site**, not the real dealership. Still open.
- **Malouf Ford Lincoln: 34 listings all priced at exactly $495** regardless of MSRP (looks like a scraped fee, not the real price). Still open.
- **5-6 residual Ford make-mismatches at Nielsen Ford locations** — non-Ford vehicles (Chevy Tahoe, Jeep Cherokee/Wagoneer, Kia Sorento, Hyundai Santa Cruz, Nissan Rogue) labeled `make: "Ford"` with fabricated Ford-prefixed VINs. Still open.
- **Two uncoordinated schedulers for the Porsche daily crawler** (OS crontab + PM2's own `cron_restart`) both writing to the same output files — not corrupting anything yet, but a real race-condition risk. Still open.
- **Ford's null model/price/image cluster root-caused to two dealers**: Tom's Ford and Maplecrest Ford of Mendham — their scraper template appears to fail outright, not a general extraction problem. Still open.
- **Jack Daniels Porsche (Upper Saddle River, NJ) — reportedly the largest Porsche dealership in the country — was missing from the configured dealer list entirely.** Found 08-28 when the user asked where it appeared in the coverage audit and it wasn't there under any name. **Fixed**: added to `dealers.json` (216 dealers now), deployed to `porsche-tracker` and `porsche-finder-tracker`, committed to the repo. Not yet crawled for the first time.

## Medium / needs follow-up

- Real per-dealer geocoding (lat/lng) doesn't exist in the `dealers` DB table or the distance-badge calculation — see note above.
- **Ford coverage: 1,153 of 1,827 dealers collecting (63%), up from 17 at the start of 08-28's audit.** Remaining 674: 343 never actually attempted by any crawl batch (easiest next win — a plain crawl, no diagnosis needed, running now), ~302 returned zero vehicle URLs (real reason unconfirmed — could be Vercel/Cloudflare/Akamai bot-blocking, a wrong sitemap path, or genuinely empty inventory; needs the same live-reprobe treatment Porsche got), ~23 still-recoverable stragglers, 6 extraction-template failures.
- **Chevrolet coverage: 1,333 of 1,925 dealers collecting (69%).** 66 recoverable (crawled successfully, data lost before syncing — not yet re-run), 526 not yet reached/reason-classified.
- **Porsche coverage: 190 of 216 dealers collecting (88%), up from ~41-42 (the ~19-20% ceiling documented in the original overnight audit).** Fixed 08-28 by adding a second discovery path — Porsche's own official nationwide inventory search (`finder.porsche.com`), reached via a stealth-patched headless browser (`patchright`) instead of scraping each dealer's own site. Confirmed live: plain HTTP and even a vanilla headless browser both get blocked by Porsche's Vercel "Security Checkpoint" (bot-fingerprint detection, not just IP reputation) from the crawler box's IP — `patchright` specifically evades that fingerprinting and gets through reliably. Root-caused via a live per-dealer classification (see `scrapers/lightsail-crawler/overnight-analysis-report.md` for the original breakdown: 115 Vercel checkpoints, 19 Cloudflare/WAF, 19 unreachable, 10 wrong sitemap path, 10 no real inventory in sitemap). This same technique does **not** transfer to Ford (`ford.com/inventory`) or Acura (`acura.com/inventory-results`) — both are blocked by Akamai with a static "Access Denied" (no JS challenge to solve), confirmed live including with `patchright`; that class of block needs a paid residential/rotating proxy service instead.
- Ford has zero real day-over-day change history yet (crawler baseline is very new).
- Most filters (Trim, State, Body Style, Price Range, Days on Lot) correctly narrow results but never show a removable "chip" the way Make/Model/Sort do — users get no visual confirmation of what's currently applied.
- Mojibake in rendered text — "Coupé" showing as "CoupÃ©" (an encoding issue somewhere in the pipeline).
- Price-drop badge visually clips/overflows on large discount amounts.
- The Sold/Removed feed shows a garbled "0 Porsche" title.
- Mobile layout (375px width): the condition badge overlaps the mileage badge on vehicle cards, and dealer names wrap badly.
- trimscout.com had no Open Graph or Twitter Card meta tags at all, so link previews in iMessage/Slack/Twitter had nothing to render. **Fixed 08-28**: added real OG/Twitter metadata plus a dynamically-generated, on-brand `og:image` (no static asset existed to reuse). Deployed and confirmed live.
