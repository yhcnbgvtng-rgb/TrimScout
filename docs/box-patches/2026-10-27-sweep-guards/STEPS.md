# Box patch: sweep guards (box2) — stop retiring live cars

Code and docs only. **Nothing is installed and no box was touched.** Install only on Paul's typed **GO**, in an idle window, one numbered step at a time. Box2 is both the deals box (`/opt/trimscout-deals`, MariaDB, pm2 `trimscout-deals-api`) and a crawl box (`~/inventory-sync`). Addresses and paths: `docs/BOXES.md` (box2 = `ssh box2`).

## Why (audit 2026-10-27, read-only)
Box2's sync retired 81,268 cars on 10-27. 32,068 of them had the same VIN live at another store, and about 23% of a week's retirements were live again at the same dealer within 7 days. Two causes, both visible in the logs:

- **A store's site answered 403/429/5xx part-way through the crawl.** Fred Beans Acura of Abington had 2,125 cars, logged `HTTP_429 — waiting 45s and retrying once`, then extracted 279. The sweep retired the other 1,888.
- **Sister rooftops share one group inventory.** Blaise Alexander State College lost ~1,270 cars the night Altoona's site stopped answering 429/403 and listed them; Performance Ford Somerville / East Hanover / Randolph do the same with VIN 1FTFW1RG9TFC24061.

## What changes
| Rule | Where | Behaviour |
|---|---|---|
| 1. Never retire a VIN that is live elsewhere | deals API (`inventorySweep.js`) | a stale row is skipped while the same VIN has a **live row at another store that was seen more recently**. "More recently" stops two stale copies shielding each other forever: only the older one is protected. |
| 2. Skip a store whose crawl hit a wall | sync client (`syncSweepGuard.js`, `syncRun.js`) + deals API | the client reads tonight's crawl logs and leaves out stores with a 403/429/5xx (including a mid-crawl 429 retry) and logs each one. The API also skips any store with ≥10 live cars whose **fresh rows are under 50% of its live rows** and returns it in `skipped`. Skipped stores neither retire nor count a miss. |
| 3. Two consecutive healthy crawls | deals API + 2 new columns | a missing car is counted (`sweep_miss_count`, `sweep_miss_at` = the run's cutoff) and retired only on the **second** sweep, in a different run, that found it missing. A retried or resumed run counts once. A re-upload ends the streak (no change to the upsert needed). |

Everything is **opt-in per request**: a sync client without the new fields (box1, box3, box4, and box2 until step 6) gets byte-for-byte the old statement and response. The new client refuses to sweep at all (sends a harmless probe first) if the API does not acknowledge the guards, so it can never silently retire unguarded.

### Known consequences (decide before GO)
- **First night after step 6 retires almost nothing** (every missing car is only counted); the night after catches up. Buyers see sold cars for about one extra day. This is the intended trade.
- **Sister-store duplicates can appear in search**: before, the first-miss sweep incidentally retired the older store's copy of a re-homed VIN; now both rows stay live until the older one has missed twice *and* the newer row is gone. If that shows up, the existing `RETIRE_DUPLICATE_VINS=1` step (vinKeeper.js, currently off) is the tool for it; this change does not turn it on.
- The retired-VIN CSV (`~/sweep-retired`) and the "came back" log line now describe cars the sync **stopped vouching for**, not cars retired that night; the numbers will drop sharply.
- Only box2 is covered. Boxes 1, 3 and 4 keep their old clients and old behaviour until they get the same three client patches.
